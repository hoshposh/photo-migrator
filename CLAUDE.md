# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Go CLI (`photo-migrator`) that moves a Google Photos library from one account to another. It reads a Google Takeout export of the source account (a directory of `.zip` files or an already-extracted directory) and uploads it to the destination account through the Google Photos Library API. All progress is kept in a local SQLite file (`migrator.db`), so runs can be resumed and repeated safely. The README covers end-user setup (Google Cloud project, OAuth consent screen, Takeout).

## Commands

Tools (`go`, `task`, `golangci-lint`, `sqlite3`) are installed with `mise install` (see `.mise.toml`). The Go version in `.mise.toml` must match the `go` line in `go.mod`, so change both together. Builds use `CGO_ENABLED=0`, because the SQLite driver is `modernc.org/sqlite` (pure Go).

```bash
task build                 # go build -> ./photo-migrator (version from git describe, "dev" when not in a git repo)
task test                  # go test -v -count=1 ./...
task lint                  # golangci-lint run ./...
task vet                   # go vet ./...
task fmt                   # gofmt -w .
task ci                    # lint -> test -> build

go test -run TestRestoreMetadata_GPS ./internal/metadata/   # a single test

task db:status | db:zips | db:errors | db:shell    # inspect migrator.db (DB=path to override)
```

- Tests live in `internal/metadata`, `internal/auth`, `internal/takeout`, `internal/store` and `cmd/photo-migrator`. The store tests build a database at an older schema version with `goose.UpTo` to test a data migration. The metadata tests run the real `exiftool` binary and fail if it isn't installed. The command tests run the full Cobra tree with a temporary `HOME` and working directory; reuse their `execute` helper, which resets the global viper state. The auth tests run the real sign-in flow against a fake token server, with the package variable `openBrowser` replaced by a fake browser.
- To try the CLI safely, give it its own `--db-path` and `HOME` so it doesn't touch the real ledger, config or OAuth token.

## Architecture

The flow is: `cmd/photo-migrator/main.go` (Cobra commands plus all the orchestration logic) → `takeout` (find, extract and walk files) → `pipeline` (worker pool) → `photos` (REST client) and `store` (SQLite ledger).

- **Zip mode and dir mode.** `takeout.IsZipMode` checks whether `--takeout-dir` contains any `.zip` file. In zip mode, `processZips` handles one zip at a time, in alphabetical order:
  1. Extract into `<staging-dir>/<zip-stem>/`.
  2. Walk the extracted files and upload them.
  3. Delete the extracted files (`os.RemoveAll`) whether or not the uploads succeeded.
  4. Mark the zip `complete` only if `AllZipItemsComplete`. Otherwise it is marked `error`, and `GetPendingZips` (`status != 'complete'`) picks it up again on the next run.

  Dir mode walks the original directory in place.
- **How the ledger identifies files.** In zip mode a file is identified by (`source_zip`, `zip_entry`), its path inside the zip. `WalkDirectory` computes the entry as the path relative to the extraction root. That makes the staging directory irrelevant: `RegisterMedia` upserts on that pair and refreshes `source_path` to the current staging path, and every status update (`SetMediaComplete`, `SetMediaError`, …) looks rows up by `source_path`. In dir mode the identity is `source_path`. Migration 00003 backfilled `zip_entry` and merged rows left over from an earlier staging-dir change. Don't go back to looking rows up by staging path.
- **Producer and consumers.** `processDirectory` runs `takeout.WalkDirectory` in a goroutine. For each file it registers the row in the DB, then sends a job on a channel. `pipeline.Pool` runs `workers` goroutines. Album creation goes through `singleflight` plus a second DB check inside it, so concurrent workers never create the same album twice.
- **Rejected sign-in is fatal.** When a token refresh fails (`*oauth2.RetrieveError`, such as `invalid_grant`), `doWithRetry` returns `photos.ErrAuthFailed` without retrying. The worker calls the pool's `stop`, so `Pool.Run` cancels every worker and returns the error. The file stays `pending`, not `error`. `processZips` leaves the zip `pending` and returns, and `main` prints the error, which tells the user to run `photo-migrator auth`. Producers feeding `Pool.Run` must select on a context that is cancelled once `Run` returns (see `walkCtx` in `processDirectory`), or they block forever on a full channel.
- **Interrupts (Ctrl+C).** The first SIGINT or SIGTERM cancels the context through `withSignals`. Extraction (`ctxReader` inside `ExtractZip`) and `WalkDirectory` stop at once, no new uploads start, and uploads already in progress finish: the worker passes `context.WithoutCancel` into `UploadMedia`. An interrupt is not a failure. Files that haven't started stay `pending`, and `processZips` puts the zip back to `pending` with no error. A second signal calls `exitFunc(130)`. In `main`, `exitCode` maps `context.Canceled` to exit code 130 and a one-line message. Cobra prints usage only for flag errors: the root has `SilenceErrors` set, and `SilenceUsage` is set in `PersistentPreRunE`. Anything new that waits on I/O must respect the context in the same way. On the first signal, `withSignals` calls `onStop`, and the `run` command uses it to start `reportStopping`. That prints `stopReport(pool.InFlight())`: the byte uploads still in progress with bytes sent / size, repeated every 10 s. Progress comes from `photos.WithProgress`: the worker passes a per-upload counter that `UploadBytes` updates as it sends, resetting it on a retry.
- **Upload.** Workers call `photos.UploadBytes` in parallel and hand each upload token to the pool's `batcher` (`internal/pipeline/batcher.go`). It runs in one goroutine, groups files by album, and calls `BatchCreate` with up to 50 items when a group is full or its oldest file has waited `BatchDelay` (2s). It records each file's own result by upload token. `Pool.Run` closes it after the workers stop, so files already uploaded are always sent, including after Ctrl+C. A rejected sign-in in `BatchCreate` stops the run and leaves the remaining files pending. `photos.UploadMedia` (upload plus a one-item `batchCreate`) remains as a convenience used by the client tests. `doWithRetry` retries on 429, 5xx and network errors with exponential backoff (up to 60s, 6 retries). It rebuilds the request body with `req.GetBody`, so any new request type must set `GetBody`. The `bytes_uploaded` status and `SetMediaUploadToken` exist but nothing uses them. Rate limiting lives in the client (`photos.WithRateLimit`, applied in `doWithRetry`), so `rate-limit` counts every request and retry, not files. `BatchCreate` and `CreateAlbum` hold `Client.writeMu`: Google requires one `batchCreate` at a time per user, and write calls share a per-user limit (concurrent calls get HTTP 429). Byte uploads stay parallel. `doWithRetry` honours `Retry-After` (capped at 2 minutes) and logs each retry as a warning through the logger stored in the request context by `photos.WithLogger`. The worker stores its per-file logger there, so retry lines carry `file`, `album` and `zip`; pass a context logger whenever you add a new API call.
- **Album rules** (`takeout.albumFromPath`): remove the leading `Takeout/Google Photos/`. Files directly in that folder, files in `Photos from YYYY` and `Print Order <number>` folders, and files in the special folders listed in `nonAlbumFolders` (`Archive`, `Failed Videos`) go to the library root. Any other top-level folder name becomes the album name.
- **Finding a file's JSON sidecar** (`takeout.FindSidecar`) tries, in order:
  1. `<file>.supplemental-metadata.json`
  2. `<file>.json`
  3. any `<file>.*.json`, which catches the names Takeout cuts short
  4. any JSON file in the same folder whose `title` field matches the file name

  `nonSidecarJSON` lists folder-level JSON files to skip. To support a new media type, add the extension to `mediaExtensions` in `sidecar.go` **and** to `mimeType` in `upload.go`.
- **Restoring metadata** (`restore-metadata`, on by default) runs `exiftool -overwrite_original` to write the date/time and GPS position from the sidecar into the file before upload. Errors are logged and the upload continues. In dir mode this **changes the user's original files**. Takeout exports RAW photos that Google converted to JPEG under their original `.ARW`/`.DNG`/… names, and exiftool refuses to write those. `writableTarget` detects JPEG content by its magic bytes and gives exiftool a temporary `.jpg` hard link (or a copy), then renames the result back over the original. Keep `-overwrite_original` and not `_in_place`: writing in place through the hard link would change the original file before the commit.
- **Files that are too large.** An HTTP 413 from the upload endpoint becomes `photos.ErrTooLarge`, which the worker records as status `too_large`. `store.IsDone` and `AllZipItemsComplete` treat `too_large` as finished, so it is never retried and doesn't block its zip. `GetLargeFileErrors` lists these rows for the `large-files` command, plus older `error` rows that match `HTTP 413`-style text.
- **Locked Folder files are held back.** `WalkDirectory` sets `MigrationJob.Locked` for files under `Locked Folder/`. `processDirectory` calls `store.RegisterHeld(store.StatusLocked, …)`, which inserts *new* rows as `locked` and reports whether the row is still `locked`, and never sends a held-back file to the workers. `locked` counts as done for `IsDone` and `AllZipItemsComplete`. Setting a row back to `pending` (and its zip to `pending`) releases it: the next run uploads it to the library root. Roadmap item 4 builds a review session on this. `locked-files` and `large-files` share `newManualFilesCmd`.
- **One rule decides what is migrated: `takeout.Classify`.** Given a file name, and if needed its first bytes, it returns a skip reason (`SkipMetadata`, `SkipAppleDouble`, `SkipNotMedia`) or how to migrate the file. It is used by `WalkDirectory` (bytes read from disk), by `ScanZip`/`ScanDir` (bytes read inside the zip) and therefore by `scan --skipped`, so a run and the report always agree. Change what counts as media only there. `WalkDirectory` returns a `Skipped` tally. `processDirectory` logs one summary line per zip (`logWalkSummary`) for files skipped as not media and for files held back for the first time. Per-file held-back lines are debug-level, to keep the info log readable.
- **Media recognised by content; motion-photo halves held back.** `IsMediaFile` decides by extension. For any other file, `Classify` checks the first bytes (`videoFromHead`), accepting only ISO base-media files whose `ftyp` brand means video (`videoBrands`); HEIC, AVIF and CR3 share the container but use other brands. Names matching `motionPartRe` (`….MP`, `….MP~2`, `….MP.COVER`) are motion-photo video halves. They are flagged `MotionPart`, registered with `RegisterHeld(store.StatusMotionVideo, …)` and listed by `motion-videos`; the Locked Folder hold takes precedence. Other recognised videos get `UploadName` (the name plus the real extension) and `MimeType`, which `photos.UploadMedia` sends in place of values derived from the name.
- **Pixel RAW pairs.** `Classify` sets `RawPart` (`jpeg`/`raw`) for `PXL_x.RAW-01….jpg` / `PXL_x.RAW-02.ORIGINAL.dng`. `processDirectory` holds back the half that the `raw-pairs` setting excludes (`rawPairHeld`), using `RegisterHeld(store.StatusRawPair, …)`. The default `both` changes nothing.
- **Logging:** `buildLogger` turns off zap's sampling, because sampling silently drops repeated per-file lines. Every line logged while a zip is processed carries a `zip` field (the zip's file name). `processZips` creates a per-zip logger (`zipLog`) and passes it down, and the worker adds `zip` from `job.SourceZip`. Don't add a `zip` field to individual log calls: zap would write the key twice.
- **Schema** changes are goose SQL files in `internal/store/migrations/`, embedded with `//go:embed` and applied when the DB is opened. Add a new numbered file; never edit `00001_initial.sql`. The DB is opened with `MaxOpenConns(1)`, so all writes go through one connection.
- **OAuth** (`internal/auth`): a loopback redirect flow. Each sign-in uses a random `state`, which the callback checks before accepting a code, and PKCE (`S256`), so the code exchange must present the matching verifier. Keep both if you change the flow. The token is cached at `~/.config/photo-migrator/token.json`. The scopes are `photoslibrary.appendonly` and `photoslibrary.edit.appcreateddata`. If you change them, also update the OAuth consent-screen steps in the README. `auth.Login` (used by the `auth` command) always signs in again and replaces `token.json`; `auth.GetClient` (used by `run` and `upload`) reuses the cached token.

## Configuration and known pitfalls

- Settings are resolved by Viper in this order: CLI flag > `PHOTO_MIGRATOR_<KEY>` environment variable > `~/.config/photo-migrator/config.toml` > default. Config keys use the same kebab-case names as the flags. Read path settings with `viperPath()`, which expands `~`; plain `viper.GetString` does not.
- **Bind flags to viper only in `initConfig`.** It runs as `PersistentPreRunE` and binds the flags of the command actually being run. Never call `viper.BindPFlag` while building a command: viper keys are global, and several commands define the same flag (`credentials`, `takeout-dir`, `staging-dir`, …), so each binding would replace the last and only the last-registered command's flags would be read. Defaults for keys shared across commands are set with `viper.SetDefault` in `initConfig` (using the `default*` constants), so `config show` can report them. `cmd/photo-migrator/main_test.go` tests this through `newRootCmd()`.
- **A dry run must not change upload progress in the ledger.** When `pool.DryRun()` is true, `processDirectory` skips `RegisterMedia`, `processZips` leaves zip statuses alone, and the worker returns before uploading or touching the DB. Media rows are keyed by staging path, so even a `pending` row written during a dry run, under a different `staging-dir` from the real run, would leave its zip incomplete forever. Only `RegisterZip` (discovery) still happens. `TestDryRun_DoesNotChangeLedger` covers this.
- The `config init` template in `main.go` and the `config show` key list are maintained by hand. Update both when adding a config key.
- `migrator.db`, `_staging/` and the built `photo-migrator` binary in the repo root are local working files, not source code.
